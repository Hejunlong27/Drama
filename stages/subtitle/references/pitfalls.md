## A. 工具安装

### A1 🔴 PyPI 上的 `ctc-forced-aligner` 是坏的（同名不同源）`实测`

- **现象**：`pip install ctc-forced-aligner` 编译到最后一步失败：
  `LINK : error LNK2001: 无法解析的外部符号 PyInit_align_ops`
- **根因**：PyPI 上这个包作者是 **Deskpai.com**（仓库 `deskpai/ctc_forced_aligner`），
  其 `main.cpp` **只定义了 `align_sequences`，没有 `PyInit_align_ops`**，却被 `setup.py`
  声明成 Python `Extension` ⇒ **链接必然失败，与有没有编译器无关**。
  我们要的那个（563★，BSD-2-Clause）**不在 PyPI**。
- **修法**：从 GitHub 源码装：
  `pip install https://github.com/MahmoudAshraf97/ctc-forced-aligner/archive/refs/heads/main.tar.gz`
- **判据**：真正的那个用 **pybind11**（`setup.py` 里有 `Pybind11Extension`），入口函数自动生成。

### A2 编译需要 MSVC C++ 工具链 `实测`

- **现象**：`error: Microsoft Visual C++ 14.0 or greater is required`
- **修法**：装 VS Build Tools 的「使用 C++ 的桌面开发」
  - winget：`winget install --id Microsoft.VisualStudio.2022.BuildTools --override "--quiet --wait --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"`
  - 或引导器：`https://aka.ms/vs/18/release/vs_BuildTools.exe`（约 15 KB 引导器，实体组件 2–3.5 GB）
- **注意**：`cl.exe` 不在 PATH 也正常，setuptools 会自己找。

### A3 🔴 whisper.cpp 读不了中文路径 `实测`

- **现象**：模型放在中文目录下报 `whisper_init_from_file: failed to open '<中文路径>/…'`（路径显示正常）
- **根因**：whisper.cpp 用窄字符 `fopen`，中文路径按 ANSI 代码页解释 ⇒ 找不到
- **修法**：**模型与输出目录都放 ASCII 路径**（示例：`C:\whisper-models\`）
- **同理**：whisper 滤镜的 `destination` 也在中文路径下会失败

### A4 whisper.cpp 发布包解压后有子目录 `实测`

- **现象**：解压后找不到 `whisper-cli.exe`
- **根因**：zip 内层是 `Release/` 目录
- **修法**：exe 在 `…\whisper-cli\Release\whisper-cli.exe`
- **教训**：列文件时**打印完整路径**，只打印文件名会把自己骗了

### A5 GitHub release 附件**直连**比代理快得多 `实测`

- **实测吞吐**：直连 **2259 KB/s**；`ghproxy.net` 369 KB/s；`gh-proxy.com` 172 KB/s（曾在 600 秒里只下 15.8/21.4 MB）
- **原因**：release 附件走 `objects.githubusercontent.com`，与 `raw.githubusercontent.com` 不同，**直连是通的**
- **结论**：下载 release 附件优先直连；只有 `raw`/`codeload` 类才需要代理

## B. 对齐

### B1 🔴 整段台词一起对齐 → 首句被吸走（最大的坑）`实测`

- **现象**：用户反馈"整段字幕完全没对上"，尤其段首
- **数据**：seg05 首句被推到 3.72s（真值 0.08s）；seg06 首句被推到 4.42s（真值 0.20s）
- **根因**：CTC 把全部文本在整段音频上重新分配；音频中与首句声学相似的片段把文本吸过去
- **修法**：**顺序约束的逐条对齐**（详见 `alignment.md`）
- **验证**：隔离实验 —— 只取前 3.5 秒单独对齐首句，结果完全正确

### B2 改 `--star_frequency segment` 是错的解法 `实测`

- 修好 2 处，**改坏 5 处**（seg04 由正确的 2.52 变成错误的 0.46）
- 单条对齐时 `edges`（默认）最好：`edges` → 0.08–1.94；`segment` → 尾巴拉到 3.48
- **结论**：保持 `edges`，改用顺序约束

### B3 朴素逐条对齐 → 各行区间重叠 `实测`

- seg07 两行对齐结果区间重叠（物理上不可能）⇒ 必须加"下一条从上一條结束之后"的约束

### B4 中文不加 `--romanize` → 内部断言失败 `实测`

- `AssertionError: <star> != 好`

### B5 不设 `PYTHONUTF8=1` → 读文本崩 `实测`

- `UnicodeDecodeError: 'gbk' codec can't decode byte 0xa7`
- 根因：对齐器 `open(args.text_path, "r")` 没指定编码 ⇒ 用系统默认（中文 Windows = GBK）
- 修法：`PYTHONUTF8=1`（Python UTF-8 模式），**不用改文件、不用打补丁**

### B6 对齐结果不打印到 stdout `实测`

- 写在**音频同名**的 `.txt` / `.json` 里
- **坑中坑**：别把输入文本文件命名为与音频同名，会被输出覆盖

### B7 ffmpeg 自带 whisper 滤镜的时间戳**不可复现** `实测`

- 同一文件两次运行，SRT 条目边界完全不同（`2.66/3.98/5.74…` vs `2.68/4.08/5.76…`）
- 根因：**流式实时队列**，切块边界取决于"机器处理速度 vs 音频速度"
- **用途收窄**：只能回答"**有没有对白**"；**绝不能用于字幕时间**
- 附：`queue=500ms` 与 `queue=3000ms` 输出**完全相同** ⇒ 切块不由 queue 决定

### B8 ffmpeg 滤镜里的绝对路径必须转义 `实测`

- `subtitles=C:/path/sub.ass` → `Unable to parse "original_size" option value "/Users/…"`（在 `:` 处被切断）
- 只转义冒号、或相对路径 → 同样失败
- **唯一可行**：`subtitles=filename='C\:/path/sub.ass'`（**转义冒号 + 整值单引号**）
- 相对路径按**进程 cwd** 解析，不是工作区

## C. 样式与渲染

### C1 字体缺字符 → **豆腐块**，且不报错 `实测`

- 逐个字体验过覆盖（`C:\Windows\Fonts`）：

| 字体 | 西语 `áéíóúüñÑ¿¡ÁÉÍÓÚÜ` | 中文 |
|---|---|---|
| **`msyh.ttc` 微软雅黑** | ✅ | ✅ |
| **`simhei.ttf` 黑体** | 🔴 **缺 `ñ Ñ ¿ ¡ Á É Í Ó Ú Ü`** | ✅ |
| arial/segoeui/calibri/times 等纯拉丁 | ✅ | 🔴 全缺 |

- **修法**：中文用 `Microsoft YaHei`；**西语禁用 `simhei`**；生成 ASS **前**断言字符覆盖

### C2 字体名必须是内核 family name `推断`

- 中文字体常有中英双名（如「思源黑体」vs `Source Han Sans SC`），写错会**静默回退**
- libass 的 `Fontname` **不支持 fallback 列表** ⇒ 双语同屏要用**两个 Style + 两个 Dialogue 事件**

### C3 断行把词切开 `实测`

- `老娘就说你活蹦乱跳的怎么可能得癌 / 症！把我那两万块吐出来！`（切开了「癌症」）
- 根因：无标点可用时按 `max_line_chars` 硬切
- 修法：**标点优先 + 允许 `line_tolerance_chars=3` 的容差** ⇒ 变成 `…怎么可能得癌症！ / 把我那两万块吐出来！`
- **西语必须按单词边界断行**，绝不切断单词（与中文是两套算法）

### C4 字幕画出来了但时间不对 / 或根本没画出来 `实测`

- ffmpeg 在字体名错、字号 0、路径错时**都可能正常退出**
- **必须用像素自检**（见 `quality-gates.md` 断言 3）

## D. 拼接与音频

### D1 concat list 必须是 UTF-8 无 BOM `实测`

- ASCII 写中文路径 → ffmpeg 报 `Impossible to open 'D:/??/???????/…'`
- 现象极具误导性（看起来像路径不存在）

### D2 无损拼接后音轨比画面长 ~0.03 秒 `实测`

- 每段 AAC 有编码 padding，14 段累积
- 修法：`-t <画面时长>` 截齐，或统一重编音轨

### D3 `-c copy` 拼接在参数不一致时可能"成功退出但时间戳错乱" `推断`

- ⇒ **永远不要只看退出码**，必须断言 `nb_read_frames` == Σ各段帧数

## E. 检查与度量（自己写检查时的坑）

### E1 用 silencedetect 判"有语音"会把**音乐**算进去 `实测`

- seg14 前 9.66 秒 whisper 什么都没听到（只有 `(咱們在這裡)` 带括号=非语音标记），
  而 silencedetect 判为"有语音" ⇒ 覆盖检查误报
- **修法**：用 **whisper 转写结果**（带时间戳的 SRT）作为"有语音"的判据 —— 音乐不会被转写

### E2 whisper-cli 只吃 16 kHz 单声道 WAV `实测`

- 直接喂 mp4 → **静默失败**（无输出、无报错），于是覆盖检查悄悄退回 silencedetect 而不自知
- 修法：先 `ffmpeg -i x.mp4 -vn -ar 16000 -ac 1 -c:a pcm_s16le x.wav`

### E3 语速检查把标点算进"字数" → 误报 `实测`

- `「真的？！」` 若按 4 字算：4 / 0.36s = **11.1 字/秒** → 误判"对齐错位"
- 实际只说了 2 个字 ⇒ 5.6 字/秒，正常
- 修法：**只统计会发音的字**（剔除 `！？。，、；：…—「」《》（）` 等）

### E4 覆盖检查里"段内相对时间"减错基准 → 每段都误报 `实测`

- 错法：减「该段**第一条字幕**的起点」
- 正法：减「**该段的起点**」（集内偏移）
- 症状：修好前报 27 处、合计 55 秒；修好后收敛到 5 处、23.2 秒

### E5 空值相等不算证据 `实测`

- 两个文件都不存在时，`Get-FileHash` 返回空字符串，比较结果是"完全一致" ⇒ 假阳性
- 修法：比较前先断言文件存在且非空

### E6 列表输出要打印完整路径 `实测`

- 只打印文件名会掩盖"其实在子目录里"的问题（见 A4）

## F. 教训（方法论层面，比具体坑更值钱）

1. **发现"证据"时，先怀疑测量工具，再怀疑结论。**
   曾基于"3 次时间吻合"断言"决定性证据"，后来复跑发现工具**不可复现**，那个结论站不住。
2. **样本量不够时，"看起来对上了"比"没对上"更危险**——因为它会让你停止验证。
3. **一次修复要全量回归。** 改 `star_frequency` 后只看了"修好的 2 处"，差点没发现"改坏的 5 处"。
4. **改参数之前先做隔离实验。** 否则分不清"工具错"还是"素材本来如此"。
5. **"能跑通" ≠ "画对了"。** ffmpeg 退出码 0 只代表进程正常结束。

## G. 2026-09-20 修掉的 4 个真缺陷（在 §F 之后发生，**引擎已同步**）

> 本节全部结论都用 `whisper-cli -ml 1` 的**逐字**时间戳当真值验证过，不是"跑通了就算数"。

### G1 对齐器断言失败会**炸掉整集**（阻断级）

- **现象**：`RuntimeError: 命令失败 rc=1` → 对齐器 `AssertionError: n != i` → **整集字幕全废**
- **真因**（隔离实验）：CTC 需要「音频帧数 ≥ 目标 token 数」。本管线用 `--romanize --split_size char`
  ⇒ **每个汉字膨胀成 4–5 个 token**（拼音逐字母）。ep06_seg05 第 3 句 30 字只剩 2.44 秒窗口
  ⇒ token 数超过帧数 ⇒ 内部断言崩溃。换 `--split_size word` 同样失败（`<star> != i`）
  ⇒ **是帧数问题，不是分词问题**。
- **修法**：对齐调用失败**不再抛异常**，改三级降级：
  ① 整句在 `[cursor, 段尾]` 内对齐 → ② 按标点切片、各片在**同一窗口**内对齐 → ③ 按剩余时长估算（写进 `problems` 留痕）
- ⚠️ **走过的弯路（已否掉，别再走）**：第一版是「**先**按标点切片，每片在到段尾的长窗口里对齐」
  ⇒ line 0 被拉成 `0.06–8.48`（真值 0–2.6）。因为每片都在长窗口里自由搜索，会被声学相似片段吸走。
  **必须整句优先，切片只作降级**。
- ⚠️ **另一处真 bug**：切片函数拿到的是**顶层 config** 而不是 `cfg["languages"][lang]`
  ⇒ `break_punct` 取空 ⇒ 退化成"按字符对半切"，切出来的根本不是句子。

### G2 `cps_hard_max=12` 的判据前提是错的（阻断级）

- **现象**：修好 G1 后整集被断言中止：`语速异常（>12.0 字/秒）`
- **证据**：whisper 逐字时间戳显示该句确实在 7.09–9.38 秒说完 ⇒ **12.93 字/秒是真实语速**
  （AI 配音把长台词压进短片长）。旧判据「>12 = 错位」**被实测推翻**。
- **修法**：新增 `cps_impossible`（zh 20 / es 40）= 生理上限，**只有超过它才中止**；
  `cps_hard_max`（12）降为告警。
- **并且**：「生理上限」的最终判定移到**最终会渲染出去的字幕**上（不是对齐原始记录）——
  因为段首修复会把第一条字幕起点前移（ep06_seg06 原始 0.76s → 修复后 3.94s，18.4 字/秒 是**假象**）。

### G3 段首首句被推后（质量级，**最普遍**）

| 段 | 首句真实起点 | CTC 对齐起点 | 被推后 |
|---|---|---|---|
| ep06_seg01 | **0.00** | 1.84 | +1.84s |
| ep06_seg02 | **0.00** | 5.44 | +5.44s |
| ep06_seg06 | **0.00** | 5.76 | +5.76s |
| ep06_seg07 | **0.00** | 3.96 | +3.96s |

- **成因**：CTC 的搜索窗口是 `[cursor, 段尾]`；对**第一句**来说窗口远长于台词真实跨度，
  模型会自行挑一段子区间。后续各行因顺序约束把窗口收紧了 ⇒ **只有段首错、后面都对**。
- **普遍程度**：ep04 **6/13 段**、ep05 **6/10**、ep06 **4/8**、ep07 **3/5**、ep09 **4/5**、ep10 **3/5** 中招。
- **修法**：`repair_leading_gaps()` —— 不改文本、不改行序，**只把时间外扩**：
  段首 0 秒起有语音却无字幕 ⇒ 把该段第一条字幕起点前移盖住它。

### G4 CTC 起点普遍偏晚（**不限首句**，会吃光后续音频）

- **现象**：ep10_seg05 第 2 句在 6.6 秒窗口里被放到 **9.56–12.12**（whisper 真值 **5.68–6.88**）
  ⇒ 剩余音频被吃光 ⇒ 第 3/4 句压成 **26 字/0.10s = 250 字/秒**、**15 字/0.40s** ⇒ 断言中止整集。
- **试过但没用**（记录以免重走）：换 `--star_frequency segment` → 起点**一模一样**；
  换 `--split_size word` → 另一种断言；只收窗口到「字数/3.5」→ 缺口 13.88→6.84 但**仍放错**。
- **修法（两条）**：
  - **(a) 多档窗口择优**：`wide`（`[cursor,段尾]`）/ `tight`（字数/3.5）/ `tighter`（字数/6.0），
    用缓存的 whisper 语音区间算「有语音却无字幕」总时长**打分**，后一档必须**好 0.5 秒以上**才顶替。
    ep10_seg05 由 13.88 → **0**。**「好 0.5 秒」是防回归的关键**：ep06 八段里 7 段仍选 wide 且时间一字未动。
  - **(b) 相邻台词连续性约束**：实测同段内相邻台词基本首尾相接（间隔仅 0–0.2 秒），
    若某句起点落后上一句终点 **≤2.5 秒** ⇒ 判为漂移，**把起点拉回上一句终点**（只改起点不动终点）。
    ep06_seg06 第 2 句由「晚 6 秒」变成「晚 0.94 秒且连续无空档」。
    **为什么是 2.5 秒**：间隔 >2.5s 说明中间是**剧本外语音**（音乐/他人插话），硬拉会把字幕盖到无关音频上——
    实测 ep09_seg05 间隔 **5.4 秒** 即属此类，必须不拉。

### G5 顺带推翻的一条旧口径

> 本文档及旧版 SKILL.md 曾写「whisper 时间戳较粗，**不用于字幕时间**」。
> **对中文不成立**：`whisper-cli -ml 1` 的逐字时间戳在上述疑难段上**明显优于 CTC**。
> 排查对齐问题的**第一步**就是跑它取证。

### G6 验收：没有 vision provider 也能验字幕外观

`_qa_subtitle_frame.py`（在 `short-drama-production` 包里）：
取「母版帧 vs 烧录帧」差异，**同一字幕内多帧求交集**隔离字幕像素（单帧会被高运动画面污染，
实测有 3 帧包围盒铺满全屏、差异像素 8.9–9.2 万），**且只在底部 220px 字幕带内度量**。
结果：ep03–ep10 共 **172 条字幕 0 条有问题**。

### G7 教训：Skill 里的引擎副本会静默过期

本次发现 `drama-subtitle-pipeline/scripts/subtitle.py` 是**修复前**的 748 行旧版，
而项目那份已经 1035 行（含全部 4 项修复），**而 SKILL.md 还把旧版声明为"真源"**
⇒ 任何人按该 Skill 的说明调用，都会原样复现「整集崩溃 + 首句推后」。
**改引擎之后必须 `Get-FileHash` 核对两侧一致**，别靠记忆。

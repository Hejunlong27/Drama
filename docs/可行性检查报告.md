### 2.2 依赖关系（数据接线的关键约定）

1. **`data/` 四文件是出片层统一输入契约**（`ai-video-pipeline/references/data-schema.md`）：`shots.json` / `characters.json` / `scenes.json` / `h3_prompts.json`，一律只读。
2. **`<Picture N>` 顺序编号 ↔ `character_refs[i]` 顺序喂槽**：对全部 Subject（角色/场景/道具）统一编号；缺一号后面全部错位；**H3 图片槽硬上限 6**。
3. **`<d>[语言] 台词</d>` 是字幕真源**；`[Shot N] At MM:SS` 时间戳必须与 `--duration` 一致（否则镜头节奏被等比压缩）。
4. **双状态源**：创作层 `project.json`（`state.step` / `ep_status`）与出片层 `output/<batch>/state.json`（status / task_id / usage）互不感知。

## 3. 断点清单（改造要补的洞）

| # | 断点 | 现象 | 影响 | 处置建议 |
|---|---|---|---|---|
| **B0** | **创作层依赖 WorkBuddy 会话** | 选题/世界观/剧本/分镜提示词都是「Agent 会话内技能调用」，无独立 API 入口 | 脱离 WorkBuddy 后第 0–6 环节无法自动运行 | 采用**混合模式**：创作层保留 WorkBuddy 技能（人工质量闸），执行层独立成项目；API 化列为 Phase 2（需 LLM 适配器 + 提示词工程复刻） |
| **B1** | **创作→出片数据断层（唯一 P0）** | `ai-drama-creator` 产 `storyboard/*.md`（Seedance 体系），出片引擎吃 `data/*.json`（H3 体系）；**中间无转换器**，目前靠手工整理 | 每部新剧都要手工搬数据，易错、不可复用 | 新增确定性转换器 `storyboard → shots.json / h3_prompts.json / refs 映射`，输出严格遵循现有 data-schema.md |
| B2 | 双提示词体系并存 | Seedance 分镜 vs H3 六段式两条线各自闭环 | 上游不统一，转换器要做两套适配 | 收敛：出片主体系 = H3 六段式（`<Picture N>` + `<d>` + 时间戳）；Seedance 线保留为风格备选 |
| B3 | 悬空引用 | `ai-video-pipeline` / `short-drama-production` 文档引用的 `script-to-drama-prompt-dev` 本机不存在（职能已由 `3d-short-drama-studio` 承担） | 新会话按文档找不到上游 | 文档修正引用；独立项目内消除该引用 |
| B4 | 双状态源不互通 | `project.json` 与 `output/<batch>/state.json` 各自为政 | 断点续跑要人脑合并两套进度 | 编排层新增只读聚合状态视图（不改两个文件的 schema） |

## 7. 明确结论

**总体结论：可行，建议按「编排层新建 + 引擎原样收编 + 创作层保留」改造。**

按环节分级：

| 分级 | 环节 | 理由 |
|---|---|---|
| ✅ 直接固化（零改动复用） | 锚点登记/校验/转换（cli.py）、时长审计、提示词净化器+模板、参考图接线、出片双引擎、字幕/放大引擎、像素验收、成本脚本 | 纯本地确定性代码，已实战验证，业务规则沉淀在里面 |
| 🔌 需适配器（逻辑不动，接口归一） | RunningHub 标准通道（AI 应用 + 工作流）、ffmpeg/Topaz | 只做统一入口与配置切换 |
| 🆕 需新增（补断点，不碰既有格式） | storyboard→data 转换器、ingest 门禁、统一编排器/状态视图、统一台账 | 新代码只做搬运与校验，产出 schema 全部沿用现有契约 |
| 👤 保留 LLM/人工（不改造） | 选题、世界观、FFS 剧本、H3/分镜提示词、放大后「要不要字幕」的人工停点 | 质量闸在人工；API 化是 Phase 2 可选项 |

改造工作量集中在编排层（薄）+ 一个转换器（中），引擎层零重写。
